### 1.2 매핑 사전 (`docs/BOM_Code_Mapping_Dictionary.json`)

```text
prefix_dictionary : 128개  (prefix -> dominant_description_major)
  confidence 분포  : LOW 80 / HIGH 46 / MEDIUM 2
  혼합 prefix 예   : RAA -> Coil 46% + Sheet + Resin (share 0.46)
  깨끗 prefix 예   : ADC -> Door Assembly (share 1.00, HIGH)
part_code_dictionary : 599개 (part_no 단위 description/description_major)
  DB 996개 part_no 중 exact 겹침 119개(12%)  <- 하드 게이트로는 부적합
```

- `part_code_dictionary`로 정밀 게이트 교체는 **데이터 커버리지 12% 때문에 불가** → 대신 description 토큰 정밀필터로 해결.

## 2. 문제 ② 매핑 정밀화 (가장 먼저 처리)

### 2.1 설계

prefix로 후보를 1차 narrow 한 뒤, **매핑된 description의 핵심 토큰**(예: `Door Assembly`→`door`, `Coil`→`coil`)이 행 `part_name`에 들어있는지로 **2차 정밀필터**.
- 깨끗한 prefix(ADC=Door)는 모든 행이 토큰을 포함 → 영향 없음(recall 보존).
- 혼합 prefix(RAA)는 입력과 다른 부품(Sheet/Resin)이 토큰 불일치로 제거됨.

핵심 토큰 추출 시 `assembly`, `full`, `sub` 등 일반 단어는 다른 의미 토큰이 있을 때만 제거(`Door Assembly`→`door`).

### 2.2 수정 파일

- `src/dev_parts_backend/module_mapping.py`
  - `GENERIC_DESCRIPTION_TOKENS` 상수 추가(assembly/full/sub/part/kit 등).
  - `description_tokens(value)` 추가: description에서 부품 종류를 가르는 의미 토큰만 추출.
  - `enrich_change_with_mapping()`의 `mapping`에 `share`, `primary_description_tokens` 추가.
- `src/dev_parts_backend/workflow.py`
  - `mapping_description_tokens(change)`, `description_match(change, row)` 추가.
  - `recommend_change_candidates()` 후보 루프 상단: `prefix_gate`가 켜지고 description 불일치 + exact part_no도 아니면 후보에서 제외.

### 2.3 검증 (`data/test_multi_vector.db`)

```text
입력 "Coil":
  prefix 게이트만        -> 65행 {Coil 23, Sheet 13, Resin 28, Fan 1}
  description 필터 적용   -> 23행 {Coil 23}              (무관 42행 제거)

입력 "Door Assembly"  -> bucket 11, kept 11  (recall 손실 0)
입력 "Cavity Assembly"-> bucket 6,  kept 6
입력 "Bracket"        -> bucket 50 {Bracket 41, Clamp 5, Damper 2, Window 2} -> kept 41
입력 "Cover"          -> bucket 36 {Cover 35, Supporter 1} -> kept 35
```

## 3. 문제 ① 과거데이터 빈약 대응

데이터 한계 자체는 만들어낼 수 없으므로, **희소한 변경텍스트에 덜 의존**하고 **데이터 공백을 가시화**하는 방향.

### 3.1 점수 재배분 (`workflow.py` `RERANK_WEIGHTS`)

prefix+description 게이트가 이미 부품 정체성을 보장하므로 identity 비중을 올리고, 노이즈가 큰 `change_intent_text` 의존을 낮춤.

```text
                       이전 -> 변경 후
identity_recall        0.35 -> 0.45
dense_changing_point   0.15 -> 0.12
dense_reason           0.10 -> 0.10
change_bm25            0.20 -> 0.18
change_intent_text     0.35 -> 0.22
mapping_prefix         0.15 -> 0.15
```

변경텍스트 신호(0.62)가 identity+mapping(0.60)을 압도하지 않게 조정. 라벨 데이터가 없어 큰 폭의 튜닝은 피하고 합리적 수준으로만 조정함(추후 사용자 피드백으로 재튜닝 가능).

### 3.2 변경텍스트 유무 플래그

- `workflow.py` `compact_candidate()`에 `has_change_text` 추가: 변경점/사유가 실제 기록돼 있는지 표시.
- `ui/streamlit_app.py` `candidate_table()`에 `has_change_text` 컬럼 추가 → "매칭 실패"가 아니라 "데이터 공백"임을 화면에서 구분.

### 3.3 combined 임베딩 텍스트 보강 (`embedding_csv.py` `source_texts()`)

combined 텍스트에 `part_type`, `classification`을 추가. 변경사유가 비어도 부품 정체성으로 검색되도록 함.
**주의: 효과는 `devparts embed-csv` 재생성 후 반영됨**(기존 임베딩에는 미적용).

## 4. 문제 ③ LLM 추출 개선

### 4.1 수정 내용 (`change_extraction.py`)

- 프롬프트 재작성(`extraction_messages`):
  - **원자적 분리**: 한 모듈에 변경 여러 개면 변경마다 행. 한 행 = 변경점 하나.
  - **매핑 디커플링**: module_name/part_name은 슬라이드 표기 그대로. 표준 모듈명 강제 선택 제거(매핑은 후처리 `enrich_change_with_mapping`이 담당). 사전은 "참고용 후보"로만 제공.
  - **동일성 유지**: description/module_name/part_name이 같은 모듈을 가리키게.
  - **base_part_no 규칙**: 실제 BOM 부품번호만. 모델/등급 코드(BO24, LTIS7338XE)·스펙값 금지.
- `normalize_llm_change()`: `looks_like_part_no()`로 base_part_no 검증, 부적합하면 빈 문자열.

### 4.2 수정 내용 (`module_mapping.py`)

- `known_prefixes()`: 사전의 모든 prefix 집합.
- `looks_like_part_no(value)`: 사전 prefix로 시작 + 숫자 포함 + 8자 이상만 part_no로 인정.

```text
ADC56000821 / AEV73730303 / 0CC103BK5BA -> True
BO24 / LTIS7338XE / LQEN7135XE / 137mm  -> False
```

### 4.3 검증 (실제 PPTX 라이브 추출, gpt-4.1-mini)

대상: `data/input/260309 ... Compact_Oven ... .pptx` (47 슬라이드)

```text
지표                     개선 전(16행)      개선 후(68행)
추출 행 수               16                 68 (원자적 분리)
change_point 중앙 길이   74.5자             21자
change_point 최대 길이   193자              117자
base_part_no 채움        일부               57/68
잘못된 base_part_no      BO24 x2            0
prefix 매핑              부분 + 0T 버그      63/68 정상
distinct module          ~10                52
```

- Controller Assembly -> **ACM** 정상 매핑(구 0T 버그 미재발).
- 구체적 치수 변경 보존 예: "size reduced from 3.0 cu.ft to 2.0 cu.ft", "depth reduced by 8mm", "thickness 0.7t -> 0.6t".

## 7-1. 추가 작업 (2026-06-12): Design Points BOM 표 → CSV 추출

### 배경

퀵존 PPTX의 "Design Points" 슬라이드가 곧 master=BOM이다. 각 슬라이드는 하나의
Design Point(모듈) 그룹이고, 본문에 다음 컬럼의 BOM 표가 들어 있다.

```text
No. | Lev. | Base P/No | New P/No | Part Name | UOM | Qty | 상세 변경점
```

기존 `pptx_text.py`는 표의 행/열을 무시하고 텍스트를 평문으로 이어붙여서 BOM 표가
뭉개졌다. 시연용으로 이 표를 **충실하게(가공 없이) CSV로 덤프**해야 했다.

### 수정/추가 파일

- `src/dev_parts_backend/bom_table.py` (신규)
  - PPTX 표(`a:tbl/a:tr/a:tc`)를 셀 단위로 파싱.
  - 헤더 토큰(`base p/no`,`new p/no`,`part name`)으로 BOM 표만 선별.
  - 슬라이드 제목 텍스트박스("... 작성 가이드 - <모듈명>")에서 `design_point` 추출.
  - `write_bom_dump_csv()`로 충실한 덤프 CSV 생성.
- `src/dev_parts_backend/cli.py`
  - `devparts extract-bom --pptx <경로> --output <csv>` 명령 추가.

### 출력

```text
data/output/QuickZone_DesignPoint_BOM.csv
컬럼: slide_number, design_point, no, lev, base_part_no, new_part_no, part_name, uom, qty, change_point
표 13개, 행 253개
design_point 그룹(11): Plate Assembly,Upper / Controller / Upper Oven /
  Rear Panel Ass'y(Upper) / Upper Door Assembly(풀다운) / Lower Oven /
  Rear Panel Ass'y(Lower) / Lower Door Assembly / Accessory / 전장부품(Heater,Harness,etc)
```

특수값(`TBD` 미정, `←` 변경없음, `-` 없음, `Delete/삭제`, `1 → 2` 수량변경)을

## 7-2. 추가 작업 (2026-06-12): `/changes/recommend` 타임아웃(ReadTimeout) 수정

### 증상

변경 입력이 여러 개일 때 Streamlit에서 `/changes/recommend` 호출이 120초를 넘겨
`requests.exceptions.ReadTimeout`으로 죽었다.

### 원인 (핵심 버그)

`rag/search.multi_vector_scores`가 변경 입력마다 DB 전체(detail 임베딩)를 다시
JSON 파싱 + cosine 계산했고, **요청 범위 캐시를 `conn`에 붙이려 했으나
`sqlite3.Connection`이 임의 속성 할당을 막아 조용히 실패** → 캐시가 매 호출
재빌드됐다. 변경 N개면 `N × (1068행 × 4벡터 JSON 파싱 + norm 재계산)`.
68행이면 100초 이상이 되어 120초 타임아웃에 걸렸다.

### 조치

| 파일 | 변경 |
| --- | --- |
| `src/dev_parts_backend/db.py` | 속성 할당 가능한 `Connection(sqlite3.Connection)` 서브클래스로 `connect`. 이게 요청 범위 캐시를 가능케 한 핵심 수정. |
| `src/dev_parts_backend/rag/search.py` | `_embedding_cache(conn)`: DB 임베딩을 한 번만 파싱·단위정규화해 conn에 캐싱. numpy가 있으면 필드별 (행렬, id) 로 저장해 코사인을 행렬곱 한 번으로 계산. 순수 파이썬 fallback 포함. |
| `src/dev_parts_backend/workflow.py` | `related_parts`는 1순위 후보만 계산(UI가 1순위만 표시). `get_candidate_subtree_summary` 중복 스캔 제거. `get_subtree_rows` SQL에 `LIMIT` 추가. |
| `src/dev_parts_backend/ui/streamlit_app.py` | `/changes/recommend` 호출 타임아웃 120초 → 600초(안전망). |

### 검증 (실제 DB, 1068 detail)

```text
multi_vector_scores 캐시 동작 후:  0.2900s/change -> 0.0004s/change  (약 700배)
recommend related_limit=0:         0.017s/change   (dense 완전 해결)
recommend related_limit=20:        0.502s/change   (subtree 요약이 잔여 비용)
20개 변경 end-to-end:              0.34s(related=0) / 10s(related=20)
정확성: Coil 필터 유지(Coil 15개만), dense 자기검색 detail_id=57 score=1.0
```

남은 잔여 비용(subtree 요약, 후보당 SQL 2쿼리)은 600초 타임아웃 안에서 수백 개
변경도 처리 가능하다. 더 빠르게 하려면 UI에서 "연관 부품 수"를 낮추거나 Top-K를
줄이면 된다(`related_limit=0`이면 0.017s/change).

### 7-2-추가 (2026-06-12): 변경 200개 규모 병목 — subtree per-candidate

증상: 변경점이 ~200개가 되니 recommend가 느리고, "BOM 반영" 탭에서
`/history/{id}/related`가 후보마다 매 rerun 호출되어 요청이 폭주하고 페이지가 멈춤.

진단(실측, 실제 DB):

```text
순수 SQL 검색(게이트+BM25 2회+dense 캐시): 0.010s/change -> 200개 약 2초  (문제 아님)
+ 연관/subtree(related_limit>0)            : 0.46s/change  -> 200개 약 92초 (병목)
원인: 각 변경마다 top_k 후보(10개) 전부의 subtree를 매번 전체 스캔(200×10=2000 스캔).
```

조치:

| 파일 | 변경 |
| --- | --- |
| `workflow.py` | `recommend_change_candidates`에서 `related_parts`/`candidate_subtree`를 **1순위 후보만** 계산(이전: top_k 전부). 2순위 이하는 온디맨드. |
| `api/main.py` | `GET /history/{id}/subtree` 추가(선택 후보 subtree 온디맨드). |
| `ui/streamlit_app.py` | `read_related`/`read_connected`/`read_subtree`를 `@st.cache_data`로 캐싱(rerun 재요청 제거). "연관 부품"/"하위 subtree"는 **체크 시에만** 조회(기본 OFF). |

결과:

```text
200개 + related=20 : 92초 -> 26초  (subtree 1순위만)
200개 + related=0  : 약 3초         (전부 온디맨드, 클릭 시 캐시 로딩)
BOM 반영 탭 /history/related 요청: 매 rerun N건 -> 0건(체크 전), 캐시로 재요청 없음
```

→ 대량(200+) 처리 시 권장: "연관 부품 수=0"으로 추천(순수 검색)하고, 필요한 후보만
반영 탭에서 펼쳐 보면 된다.

## 7-3. 추가 작업 (2026-06-12): Base BOM 엑셀 업로드 → 최종 마스터 BOM (회의록 GAP 2.1 해결)

### 배경

3주차 회의록의 INPUT 한 축인 **Base BOM(원본 엑셀)**이 미구현이었다
(`회의록_대비_프로젝트_점검_3주차.md`의 GAP 2.1, 최우선). 사용자가
`data/input/base_bom.xlsx`(실제 PLM BOM export, 모델 LTIS7338XE)를 제공해 이를 반영했다.

### xlsx 구조

```text
컬럼: Part No / Lvl(.1/..2/...) / Parent Part No(모) / Part Name(자) / Description /
      Technical Spec / Qty / UOM / Type / Maker / Substitute For ...
시트 1개(ag-grid), 총 3537행
```

- `Lvl`의 점 개수 = BOM depth(loader와 동일 규칙). `Description`이 코퍼스의 part_name 표기와 일치.
- `*S*` 레벨 2067행은 **대체품(Substitute For)** — 트리 노드가 아님.

### 수정/추가 파일

| 파일 | 변경 |
| --- | --- |
| `src/dev_parts_backend/base_bom.py` (신규) | xlsx를 stdlib zip/xml로 파싱 → apply 가능한 BOM rows. 헤더명 자동 매핑, depth 계산, depth-stack parent 링크. `*S*` 대체품은 트리에서 제외하고 대상 부품의 `substitutes`로 부착. |
| `src/dev_parts_backend/api/main.py` | `POST /bom/base/parse-xlsx`: base64 xlsx → {summary, rows}. rows를 기존 `/bom/apply`·`/bom/apply/export`의 `base_bom` 인자로 사용. |
| `src/dev_parts_backend/ui/streamlit_app.py` | "BOM 반영" 탭에 **Base BOM 소스 선택**(원본 엑셀 업로드 / SQLite master) 추가. 업로드 시 파싱→세션 저장→apply/export에 `base_bom` 전달. 엑셀 모드에서는 master 전용 subtree preview 비활성화. apply/export 헬퍼가 `base_bom` 인자 수용. |

### 검증 (라이브 서버, 실제 base_bom.xlsx)

```text
parse: 3537행 -> 트리 1470행, 최대 depth 7, 대체품 95개 부착, 루트=LTIS7338XE(Electric(Slide))
delete: 후보 선택 + target → 노드 + 하위 47개 트리 삭제, 1470 -> 1423  (회의록 유형3)
change: target new_part_no 갱신, classification=Change                 (회의록 유형1)
export: 유효 .xlsx(최종 마스터 BOM) 생성
```

→ 회의록의 **"Base BOM에 변경 병합 → 최종 마스터 + 변경부품리스트"** OUTPUT 경로가
SQLite master뿐 아니라 **실제 원본 엑셀**로도 동작한다.

## 7-4. 추가 작업 (2026-06-12): Changing 상향 전파(도미노) (회의록 GAP 2.2 해결)

### 배경

회의록 3단계 유형(1): 하위 단품 사양 변경 시 **상위 Assembly 품번도 도미노 상향 전파**
되어야 한다. 기존 change 액션은 target 행 하나만 갱신했다.

### 규칙(정의)

- change 또는 subtree_replace를 적용한 행의 **상위 조상(부모→루트) 전체**를 변경으로 표시.
- 상위 어셈블리는 내용이 바뀌었으므로 품번 재발행이 필요하다 → `new_part_no="TBD"`,
  `classification="Change(하위전파)"`, `applied_action="propagated_change"`.
  (실제 신규 품번은 PLM에서 부여하므로 TBD로 둠.)
- 직접 변경/추가 대상이거나 이미 전파된 조상은 덮어쓰지 않는다(중복 방지).
- 기본 ON, 토글로 OFF 가능.

### 수정 파일

| 파일 | 변경 |
| --- | --- |
| `workflow.py` | `ancestor_indexes(rows, index)`(깊이 기반 조상 체인), `propagate_change_to_ancestors(...)`. `apply_selected_changes`에 `propagate_change_upward=True` 인자 추가, change·subtree_replace 분기에서 전파 호출. |
| `api/main.py` | `BomApplyRequest.propagate_change_upward`(기본 True)를 apply·export로 전달. |
| `ui/streamlit_app.py` | "하위 변경 시 상위 Assembly로 전파(도미노)" 체크박스(기본 ON). `flatten_change_list`가 `propagated_change` 행(ancestor/after)을 표에 표시. |

### 검증 (라이브 서버, 실제 base_bom.xlsx)

```text
depth-5 부품(MGJ64430303 Plate) change:
  propagate ON  -> change 1 + propagated_change 5 (depth 4,3,2,1,0)
     TBD <- Plate,U Bending(Lower)(d4) <- Cavity Assembly,welding(d3,d2)
         <- Cavity Assembly,Full(d1) <- Electric(Slide) 루트(d0)
  propagate OFF -> change 1 (전파 없음)
  export: 유효 .xlsx
```

→ 회의록 유형(1)의 "도미노 상향 전파"가 동작한다. 남은 회의록 GAP: 2.3(NEW 연관부품
번들 추천), 2.4(부품명 alias 사전).
