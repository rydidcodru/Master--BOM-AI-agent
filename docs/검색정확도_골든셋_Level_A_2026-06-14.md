관련: `docs/RAG_확장_보고서_2026-06-14.md` (이 과제는 생성 G 없이 **retrieval + 결정론적 merge**로 확정)

---

## 0. 한 줄 요약

심의표 변경항목 텍스트로 base BOM의 정답 부품을 찾는 검색 정확도를 처음으로 **수치화**했다.
순수 어휘 검색은 **Top-5 95.7% / found@10 100%**로 강하지만,
**현행 production의 prefix gate가 정답 47개 중 16개를 아예 제외**해
found@10을 **1.00 → 0.66**으로 떨어뜨린다. master 작성(Base P/No 찾기) 용도에서는
**gate를 끄거나 soft boost로 바꾸는 것**이 1순위 개선이다.

---

## 1. 무엇을 측정했나

이 과제의 실제 흐름:

```
심의표 → master(변경이력) 작성 → base_bom 보고 변경내역 → 결정론적 merge → 최종 BOM
                    ▲
            여기서 "이 변경이 base BOM의 어느 부품인가?"를 찾는 게 retrieval의 핵심
```

- **질의(query)**: 변경항목의 `part_name` / `change_point` / `change_reason`
  (★ `base_part_no`는 일부러 제외 → exact-match 지름길 없이 순수 텍스트→부품 검색을 측정)
- **정답(answer)**: 그 변경의 `Base P/No` (base BOM에 실재하는 부품)
- **코퍼스**: Compact Oven `base bom.xlsx`의 431개 부품 행
- **라벨 출처**: 변경이력(ledger)의 change 행 47건. (변경텍스트, 정답 Base P/No)를
  ledger가 이미 갖고 있어 **수작업 라벨링 0**. `level_a_labels.json`에 저장 — 실제 심의표
  prose로 교체·증강 가능.

지표: Top-1 / Top-3 / Top-5 / found@10 / MRR.

---

## 2. 결과 (baseline, 47개 라벨)

| 모드 | Top-1 | Top-3 | Top-5 | found@10 | MRR |
| --- | --- | --- | --- | --- | --- |
| **gate 제외** (순수 어휘 BM25+identity) | 0.617 | 0.851 | **0.957** | **1.000** | 0.755 |
| **production** (prefix gate 적용) | 0.447 | 0.638 | 0.660 | **0.660** | 0.541 |

해석:
- **순수 검색은 충분히 강하다.** 정답이 항상 상위 10위 안에 있고(found@10=1.0),
  95.7%가 Top-5 안에 든다. 어휘 신호(part_name 일치)만으로도 base BOM 매칭은 잘 된다.
- **gate가 결정적으로 깎는다.** found@10이 0.66 → 정답 16개가 후보 목록에 **아예 없음**.

---

## 3. 핵심 발견 — prefix gate가 정답을 제외한다

### 원인

`module_mapping.enrich_change_with_mapping`은 `part_name`을 BOM_Code_Mapping_Dictionary의
description과 fuzzy 매칭해 **하나의 dominant prefix**로 매핑한다(`mapped_prefixes`).
그 뒤 `workflow.candidate_history_rows`가 SQL `WHERE part_no LIKE 'PREFIX%'`로
**후보 코퍼스를 그 prefix로 하드 제한**한다.

문제: **한 부품의 실제 품번 prefix가 그 부품 description의 dominant prefix와 다를 수 있다.**
예) `Plate,U Bending` 변경의 정답 품번은 `MGJ...`인데, description 매핑이 다른 prefix로
가면 `MGJ...` 행이 SQL 단계에서 통째로 빠진다 → Top-K 이전에 소멸.

제외된 16건(change_id): `11, 13, 14, 16, 20, 23, 33, 37, 64, 69, 70, 74, 76, 171, 177, 205`.

### 왜 gate가 원래 있었나 (맥락)

gate는 "혼합 prefix 버킷에서 엉뚱한 부품 종류를 떨어뜨리려" 도입됐다
(`docs/진행상황_및_수정가이드.md` 3.2-1). **대용량 다모델 history**를 검색할 땐 노이즈를
줄여 유효했을 수 있다. 그러나 **base BOM(한 모델 431행)에서 정답 부품을 찾는** 이번
용도에서는 코퍼스가 작고 깨끗해서 gate의 노이즈 억제 이득보다 **정답 제외 손해**가 크다.

---

## 4. 권장 개선 (우선순위順)

1. **gate를 하드 필터 → soft boost로.** `candidate_history_rows`에서 prefix로 코퍼스를
   제외하지 말고, 전체에서 검색하되 prefix 일치에 **가산점**만 준다(이미 `mapping_prefix`
   가중치가 있으니 점수만 살리고 SQL 제외를 제거). 정답이 사라지는 일이 없어진다.
2. **fallback 게이트.** gate된 후보군에 강한 identity 매치가 없으면(또는 비었으면)
   자동으로 ungated 검색으로 재시도.
3. **용도별 분기.** "base BOM에서 변경 대상 찾기"는 gate off, "대용량 history에서 유사
   과거변경 찾기"는 gate 유지 — 코퍼스 성격에 맞춰 분리.
4. **dense 켜기.** 현재는 base BOM에 임베딩이 없어 어휘 모드만 측정됐다. base BOM
   part_name을 임베딩하면 dense 신호로 prose 질의(동의어/표현차)에 더 강해진다.

> 1번만 적용해도 found@10이 1.0으로 회복될 가능성이 높다(순수 어휘 모드가 이미 1.0).

---

## 5. 한계 (정직)

1. **dense 미측정** — base BOM 임베딩이 없어 BM25+identity-text(어휘)만. dense 효과는
   별도 측정 필요(OpenAI 임베딩 호출).
2. **라벨이 다소 낙관적** — query의 `part_name`이 BOM `part_name`과 사실상 동일.
   실제 심의표 prose("도어 손잡이 색상 변경")는 더 거칠어 Top-1은 상한에 가깝게 봐야.
   → 다음 단계: `level_a_labels.json`을 실제 심의표 추출 텍스트로 교체.
3. **N=1** — Compact Oven 1건. 가중치/게이트 튜닝의 신뢰도엔 케이스 추가가 필요.
4. **코퍼스 = base BOM only** — gate의 가치는 대용량 history에서 다를 수 있다(4-3 참고).
