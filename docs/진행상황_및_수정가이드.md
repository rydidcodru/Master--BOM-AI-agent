## 1. 현재 확정 구조

현재 프로젝트는 아래 구조로 동작하도록 정리되어 있다.

```text
Streamlit Frontend
  -> FastAPI Backend
    -> SQLite DB file
```

- 프론트엔드: Streamlit
- 백엔드: FastAPI
- DB: SQLite 파일
- 기본 DB 경로: `data/dev_parts.db`
- 기본 백엔드 주소: `http://127.0.0.1:8000`
- 기본 프론트 주소: `http://127.0.0.1:8501`

## 2. 실행 방법

백엔드와 프론트엔드를 한 번에 실행한다.

```powershell
uv run devparts app
```

분리 실행이 필요하면 아래처럼 실행한다.

```powershell
uv run devparts serve
uv run devparts ui
```

Streamlit에서 호출할 FastAPI 주소를 바꾸려면 환경변수 또는 화면의 `FastAPI URL` 입력값을 사용한다.

```powershell
$env:DEV_PARTS_API_URL="http://127.0.0.1:8000"
uv run devparts ui
```

### 3.1-1 임베딩 CSV 생성 및 DB 적재

권장 흐름:

```text
원본 CSV
  -> 임베딩 컬럼이 추가된 중간 CSV
    -> SQLite DB 적재
      -> FastAPI 검색
        -> Streamlit에서 확인
```

중간 CSV 생성 명령:

```powershell
uv run devparts embed-csv `
  --input "data/input/detail.csv" `
  --output "data/input/detail_multi_embedded.csv"
```

생성되는 컬럼:

```text
changing_reason_embedding
changing_point_embedding
part_name_embedding
combined_embedding
```

DB 적재 명령:

```powershell
uv run devparts load-csv `
  --master "data/input/종합master.csv" `
  --detail "data/input/detail_multi_embedded.csv" `
  --reset
```

참고: 현재 `data/input/종합detail_embedded.csv`는 기존 단일 `changing_embedding`이 들어있는 파일이다. 새 loader는 이 값을 `combined_embedding`으로도 복사하므로 Dense combined 검색은 가능하지만, reason/point/part_name별 Dense 검색까지 하려면 `embed-csv`로 새 중간 CSV를 만들어야 한다.

### 3.2 추천 및 BOM 반영 로직

구현 파일: `src/dev_parts_backend/workflow.py`

현재 동작:

1. PPT/LLM에서 정리된 변경 입력 JSON을 받는다.
2. `docs/BOM_Code_Mapping_Dictionary.json`의 prefix 매핑으로 `description`, `module_name`, `part_name`을 먼저 보강한다.
3. FastAPI가 입력의 `change_reason`, `change_point`, `part_name`, combined text를 자동 임베딩하려고 시도한다.
4. `base_part_no`가 있으면 강하게 우선 매칭한다.
5. SQLite에 적재된 `changing_reason_embedding`, `changing_point_embedding`, `part_name_embedding`, `combined_embedding`과 cosine similarity를 계산한다.
6. SQLite FTS5 `bm25()`로 `changing_reason`, `changing_point`, `part_name`, `base_part_no`, `new_part_no`를 검색한다.
7. Dense 점수와 BM25 점수를 섞어 최종 후보 점수를 만든다.
8. 후보별 상위/하위 BOM 연관 부품을 함께 제공한다.
9. 사용자가 후보를 선택하면 `change`, `add`, `delete` 액션으로 base BOM을 재작성한다.

현재 점수식:

```text
1차 후보군 포함:
  - module_name / part_name / base_part_no / new_part_no 중심
  - changing_point / changing_reason만 맞는 row는 후보군에서 제외

identity_recall =
  0.45 * dense_part_name
+ 0.30 * module_part_bm25
+ 0.15 * identity_text
+ 0.10 * dense_combined

final_score =
  0.35 * identity_recall
+ 0.15 * dense_changing_point
+ 0.10 * dense_reason
+ 0.20 * change_bm25
+ 0.35 * change_intent_text
+ 0.15 * mapping_prefix
```

변경 의도 검색:

```text
module intent:
  description/module_name/part_name -> prefix gate
  예: Cavity Assembly -> ABU

change intent:
  change_type + target_value + change_intent_keywords + change_point + change_reason
  예: dimension + 137mm + 치수/축소/width/dimension

검색:
  prefix 후보군 안에서 change intent BM25/text score를 강하게 반영
```

동의어 확장 예:

```text
착탈 / 탈착 / 분리 / removable / detachable
치수 / 사이즈 / width / height / dimension / mm
스팀 / steam / stema
축소 / 감소 / reduce
```

### 3.2-1 Prefix 매핑 딕셔너리 기반 후보 제한

구현 파일:

```text
src/dev_parts_backend/module_mapping.py
src/dev_parts_backend/api/main.py
src/dev_parts_backend/workflow.py
```

사용 파일:

```text
docs/BOM_Code_Mapping_Dictionary.json
```

현재 적용된 방식:

```text
description/module_name/part_name
  -> prefix_dictionary의 dominant_description_major와 매칭
  -> 1순위 description의 prefix를 mapped_prefixes로 설정
  -> base_part_no 또는 new_part_no가 해당 prefix로 시작하는 row만 후보 포함
  -> 그 후보 안에서 Dense + BM25로 변경점/변경사유 유사도 재정렬
```

예시:

```text
입력 description: door assmbly
매핑 결과: Door Assembly -> ADC
후보 제한: base_part_no 또는 new_part_no가 ADC로 시작하는 row
랭킹: changing_point/changing_reason Dense + BM25로 정렬
```

보조 유사 후보(`Decor Assembly`, `Motor Assembly` 등)는 `mapping.matched_prefixes`에 설명용으로 남기지만, 실제 후보 게이트에는 `mapping.gate_prefixes`만 사용한다.

`OPENAI_API_KEY`가 없거나 API 호출에 실패하면 입력 자동 임베딩은 건너뛰고 BM25 또는 fallback text score로 응답한다. 중간 CSV에 기존 `changing_embedding`만 있으면 loader가 이를 `combined_embedding`으로 복사한다.

Windows에서 Python SSL/OpenAI SDK 경로로 `OPENSSL_Applink` 오류가 날 수 있어, 임베딩 API 호출은 `src/dev_parts_backend/embeddings.py`에서 `curl.exe` 기반 REST 호출로 처리한다.

### 3.2-2 PPTX 입력 및 LLM 변경 항목 추출

구현 파일:

```text
src/dev_parts_backend/pptx_text.py
src/dev_parts_backend/llm.py
src/dev_parts_backend/change_extraction.py
src/dev_parts_backend/api/main.py
src/dev_parts_backend/ui/streamlit_app.py
```

현재 적용된 흐름:

```text
Streamlit file_uploader 드래그앤드롭
  -> PPTX bytes를 base64 JSON으로 FastAPI 전송
  -> pptx_text.py가 ppt/slides/slide*.xml에서 슬라이드별 텍스트 추출
  -> change_extraction.py가 LLM에 슬라이드 텍스트 + BOM description 사전 전달
  -> LLM은 변경 항목을 JSON rows로 추출
  -> description/module_name/part_name을 매핑 사전 description 형태로 정규화
  -> data/output에 중간 추출 CSV 저장
  -> 추출 row를 Streamlit 변경 입력 표에 자동 채움
  -> 이후에는 저장된 CSV를 다시 업로드해서 LLM 호출 없이 재사용 가능
  -> 사용자가 수정 후 기존 추천 검색 실행
```

PPTX 추출 API:

```text
POST /pptx/extract-changes
```

요청 형식:

```json
{
  "filename": "change.pptx",
  "content_base64": "...",
  "use_llm": true,
  "llm_model": "gpt-4.1-mini"
}
```

응답 핵심 필드:

```text
slides[]       슬라이드 번호와 추출 텍스트
changes[]      추천 검색에 바로 넣을 수 있는 변경 입력 row
output_csv     data/output에 저장된 중간 CSV 경로/row 수/컬럼 목록
llm_status     LLM 호출/실패/fallback 상태
raw_llm        LLM 원본 JSON 응답
```

중간 CSV 저장 위치:

```text
data/output/{pptx파일명}_extracted_changes_{YYYYMMDD_HHMMSS}.csv
```

CSV 컬럼:

```text
change_id
slide_number
description
module_name
part_name
base_part_no
change_point
change_reason
change_type
target_value
change_intent_keywords
evidence
primary_prefix
mapped_prefixes
```

변경 의도 필드:

```text
change_type
  dimension / structure / material / color / electrical / mechanical / other

target_value
  137mm, 6.8inch처럼 변경 목표 수치가 있을 때 기록

change_intent_keywords
  치수, 축소, width, dimension, 착탈, detachable, steam 등 검색용 키워드
```

LLM 호출은 `src/dev_parts_backend/llm.py`에서 `curl.exe` 기반 REST 호출로 처리한다. 기본 모델은 `gpt-4.1-mini`이며, 환경변수 `DEV_PARTS_LLM_MODEL` 또는 요청의 `llm_model`로 변경할 수 있다.

`OPENAI_API_KEY`가 없거나 LLM 호출이 실패하면 rule-based mapping fallback으로 동작한다. 이 경우 슬라이드 텍스트 안에 `Door Assembly`처럼 매핑 description이 명확히 보이는 항목만 draft row로 만든다.

### 3.4 Streamlit 프론트엔드

구현 파일: `src/dev_parts_backend/ui/streamlit_app.py`

현재 화면 흐름:

1. `변경 입력 및 추천`
   - PPTX 파일을 드래그앤드롭으로 업로드
   - 슬라이드별 텍스트 추출 및 LLM 기반 변경 항목 추출
   - 추출 결과는 중간 CSV로 `data/output`에 저장
   - 기존 추출 CSV를 업로드해서 LLM 호출 없이 재사용 가능
   - PPT/LLM/CSV에서 추출한 변경 내역을 하나의 스크롤 가능한 표에서 입력 또는 수정
   - `Top-K`, 연관 부품 수 설정. 기본 Top-K는 10개다.
   - 사이드바의 `입력 자동 임베딩`으로 FastAPI query embedding 생성 여부 설정
   - FastAPI의 `/changes/recommend` 호출
   - 추천 후보, 점수 구성, 1순위 연관 부품 확인
   - 후보 테이블은 `part_name`, 변경사유, 변경점, `base_part_no`, `new_part_no`를 앞에 두고 score/detail_id/dense 점수는 뒤쪽에 배치한다.

2. `BOM 반영`
   - base BOM master 선택
   - 변경 항목별 후보 선택
   - 선택 후보 하위 품목 subtree 확인
   - `하위 포함`을 선택하면 후보 subtree와 base target subtree diff preview 표시
   - `change`, `add`, `delete` 액션 선택
   - FastAPI의 `/bom/apply` 호출
   - 결과 미리보기
   - FastAPI의 `/bom/apply/export`를 통해 `new_bom.xlsx` 다운로드

3. `데이터 확인`
   - master 목록 확인
   - 현재 추천 결과 JSON 확인

중요: Streamlit은 SQLite를 직접 읽지 않는다. 모든 데이터 처리는 FastAPI를 통해서만 수행한다.

### 5.2-2 렉/성능 이슈 확인 위치

주요 원인:

```text
1. PPTX에서 여러 change row가 추출된 상태로 후보 추천 실행
2. 각 change row마다 Dense/BM25/related parts 계산
3. 자동 임베딩이 켜져 있으면 row별로 OpenAI embedding 호출
4. Streamlit이 rerun될 때 추천 input JSON, 슬라이드 원문, 연관 부품 표를 다시 렌더링
```

현재 완화한 내용:

```text
- prefix 매핑이 잡힌 경우 전체 DB가 아니라 prefix 후보만 SQL로 조회
- Dense similarity도 prefix 후보 detail_id 안에서만 계산
- 추천 상세 JSON은 기본 숨김
- 슬라이드별 추출 텍스트는 체크했을 때만 표시
- 연관 부품 수 기본값을 5로 낮춤
```

추가로 더 빠르게 확인하려면:

```text
- 테스트 중에는 "입력 자동 임베딩" 체크 해제
- "연관 부품 수"를 0으로 설정
- PPTX는 한 번만 LLM 추출 후 data/output CSV를 재사용
- Top-K를 5 이하로 낮춤
```

## 6. 현재 제한 사항

1. PPTX 텍스트 추출은 구현되어 있으나 이미지/도형 안의 텍스트 OCR은 아직 없다.
2. 실제 `base_bom.xlsx` 업로드 후 반영은 아직 미구현이다.
3. `data/input/종합detail_embedded.csv`는 기존 단일 `changing_embedding` 파일이다. reason/point/part_name별 Dense 검색까지 하려면 `devparts embed-csv`로 새 중간 CSV를 생성해야 한다.
4. BOM 반영 규칙은 1차 MVP이다. 복잡한 추가/변경 케이스는 사용자 검증 규칙을 더 받아야 한다.
5. XLSX 출력은 기본 표 형태이며, 고급 서식은 아직 없다.
