## 1. 차이점 (구현은 됐으나 접근/방식이 다른 것)

### 1.1 모듈명 불일치 해결 방식

- **회의록**: PPT용어↔공식부품명 **동의어 사전(Alias Map)** + 정규화로 해결.
  (예: `side LED, LED, LED Side → LED Side`)
- **프로젝트**: LLM 추출 + **prefix 매핑 사전**(`BOM_Code_Mapping_Dictionary.json`)으로
  description→prefix(예: Door Assembly→ADC) 게이트 후, prefix 버킷 안에서
  description 핵심토큰으로 다른 부품을 떨어뜨림.
- **평가**: 목적은 같으나 단위가 다르다. 프로젝트는 **모듈(어셈블리) 단위** 정규화는
  잘 되지만, **부품명 단위 alias**(side LED→LED Side 같은 표기 흔들림)는 아직 없다.
  → 1.2의 "없는 점"으로 연결.

### 1.2 시맨틱 검색 엔진

- **회의록**: FAISS 기반 벡터 검색 제안.
- **프로젝트**: FAISS 없이 SQLite에 임베딩을 저장하고 numpy 행렬곱으로 cosine 계산.
- **평가**: 현재 데이터 규모(detail 1068, 임베딩 ~1068)에서는 FAISS가 **불필요**하다.
  numpy 직접 계산이 더 단순하고 의존성도 적다(→ 3.1 참고). 규모가 수십만 행으로
  커지면 그때 FAISS/sqlite-vec 도입 검토.

### 1.3 임베딩 대상 텍스트

- **회의록**: '변경사유 + 변경점' 결합 텍스트 1종.
- **프로젝트**: `changing_reason / changing_point / part_name / combined`의 multi-vector.
  combined에는 part_name·part_type·classification까지 포함(보강됨).
- **평가**: 프로젝트가 더 풍부. 단, **과거 데이터의 변경사유 47%·변경점 24%만 채워져**
  있어 변경 텍스트 임베딩의 실효는 제한적(별도 작업기록 문제 ① 참고).

### 1.4 추가된 것 (회의록에 없던 프로젝트 고유 기능)

- **Design Points BOM 표 충실 추출**(`bom_table.py`, `/pptx/extract-bom`):
  PPTX의 BOM 표를 셀 단위로 CSV 덤프. 회의록 1단계의 "변경 부품 리스트" 입력을
  결정론적으로 만드는 보조 경로. (LLM 추출과 별개)
- **prefix description 정밀 게이트**: 혼합 prefix에서 다른 부품 제거(작업기록 문제 ②).

## 2. 없는 점 (회의록이 요구하나 프로젝트에 미구현 = GAP)

### 2.1 Base BOM(원본 엑셀) 업로드 ✅ 해결됨 (2026-06-12)

- **회의록**: INPUT은 PPTX + **Base BOM(원본 엑셀)**. 변경을 Base BOM에 병합해 최종 마스터 생성.
- **반영 결과**: `base_bom.py`(xlsx 파서) + `POST /bom/base/parse-xlsx` +
  Streamlit "BOM 반영" 탭의 **Base BOM 소스 선택(엑셀 업로드)**. 업로드한
  `base_bom.xlsx`(1470행 트리)를 base로 change/add/delete 반영 후 최종 마스터 xlsx 다운로드까지 확인.
- **상세**: `작업기록_2026-06-11_검색매핑추출_개선.md` 7-3절.

### 2.2 Changing 시 상위 Assembly로의 도미노 상향 전파 ✅ 해결됨 (2026-06-12)

- **회의록 유형(1)**: 하위 단품 사양 변경 시 **상위 Assembly 품번도 연쇄(도미노) 갱신**.
- **반영 결과**: `ancestor_indexes` + `propagate_change_to_ancestors`로 change/subtree_replace
  적용 행의 조상(부모→루트)을 모두 `new_part_no=TBD`, `classification=Change(하위전파)`로 표시.
  `propagate_change_upward`(기본 ON, UI 토글). depth-5 변경 시 상위 5개 전파 검증 완료.
- **상세**: `작업기록_2026-06-11_검색매핑추출_개선.md` 7-4절.

### 2.3 NEW 부품 추가 시 연관 주변부품 자동 추천 ✅ 해결됨 (2026-06-12)

- **회의록 유형(2)**: 신규 부품 추가 시 연동 주변부품(모터→고정 브라켓/나사류) **함께 추천**.
- **반영 결과**: `get_connected_parts`(형제+하위) + `GET /history/{id}/connected` +
  add 시 멀티셀렉트로 연동 부품 선택 → `bundle_detail_ids`로 함께 추가(action=`add_bundle`).
  HITL 승인분만 추가. 실제 데이터에서 Bracket/Screw 형제 추천 확인.
- **상세**: `작업기록_2026-06-11_검색매핑추출_개선.md` 7-5절.

### 2.4 부품명 단위 Alias(동의어) 사전

- **회의록 1단계**: PPT용어→공식부품명 alias map(예: Fan Blade/Fan→`Fan,Convection`).
- **현재**: 의도 동의어(CHANGE_SYNONYM_GROUPS: 착탈/탈착 등)와 prefix 매핑은 있으나,
  **부품명 표기 흔들림을 공식명으로 정규화하는 alias 테이블**은 없음.
- **구현 위치**: `module_mapping.py`에 alias map(JSON) 추가 후 추출/검색 전 정규화.

### 2.5 Few-Shot 프롬프트(다중 예시)

- **회의록**: Few-Shot Prompting으로 정밀 추출.
- **현재**: 추출 프롬프트에 **예시 1개 + 규칙**(원자적 분리 등)으로 개선됨. 다중 few-shot은 아님.
- **평가**: 경미한 GAP. 추출 품질이 부족하면 대표 슬라이드 2~3개 예시를 추가.

## 3. 불필요한 점 / 정리 대상 (프로젝트에 있으나 회의록 기준 군더더기)

### 3.1 FAISS 미사용은 오히려 적정

- 회의록이 제안한 FAISS는 현재 규모에서 **불필요**. 도입했다면 과한 의존성이었을 것.
  지금처럼 numpy cosine 유지가 맞다. (규모 커지면 재검토)

### 3.2 `/rag/ask` 스텁 엔드포인트

- `api/main.py`의 `/rag/ask`(answer_stub)는 초기 스켈레톤 잔재로, 현재 파이프라인
  (추출→추천→반영)과 무관. 데모/운영에 불필요 → 제거 또는 보류 표시 권장.

### 3.3 레거시 단일 `changing_embedding` 컬럼

- multi-vector(`combined_embedding` 등) 도입 후 `changing_embedding`은 호환용 잔재.
  loader가 이를 combined로 복사하는 보정만 함. 신규 데이터는 multi-vector로 충분 →
  장기적으로 정리 대상.

### 3.4 입력 자동 임베딩(auto_embed) 상시 ON

- 변경 입력마다 쿼리 임베딩을 만드는데, 과거 변경 텍스트가 희소해 효과 대비 비용/지연이
  큰 경우가 있음. 데모/테스트에서는 OFF가 합리적(이미 토글 제공). **기본값을 상황에 맞게**
  재검토(불필요한 OpenAI 호출 절감).

## 5. 결론

- **2단계(History 검색)와 3단계의 Delete**는 회의록 설계와 **거의 일치하거나 그 이상**으로 구현됨.

  이 둘이 회의록의 "Base BOM에 병합해 최종 마스터 도출"이라는 OUTPUT 정의를 완성하는 핵심.
- 부품명 alias 사전(2.4)은 1단계 정확도를 끌어올리는 비교적 명확한 다음 작업.
- FAISS·`/rag/ask`·레거시 임베딩 등은 현 규모에서 불필요하므로 도입/유지 부담을 줄이는 방향이 맞다.
