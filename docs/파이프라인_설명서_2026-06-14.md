> **정정 (2026-06-14, 사용자 확인):** 이 시스템의 **주인공은 심의표의 변경점(Design Points)**
> 이다. 그 표 자체가 거의 master 초안(=정답지)이고, 이걸 그대로 master로 쓰면 BOM이 거의 완성된다.
> 시스템은 **신규 번호를 자동 추천하지 않는다** — 변경점을 명확히 보여주고, 사용자가
> **New P/No를 부여(새 번호가 필요하면 `TBD`)** 하게 하며, "과거엔 이렇게 바뀌었다"는 **참조(옵션)**
> 로만 제시한다. 연관(상위/하위) 부품도 함께 master에 들어가야 BOM이 완성된다.
> → React에 **`① 변경점 작성`** 탭(`/pptx/extract-bom`)이 이 흐름의 메인이고,
> 과거 이력 검색(아래 매칭 B)은 그 옆의 **참조 보조**로 격하되었다.

> **업데이트 (2026-06-15):** 담당자 피드백 7건 반영으로 UI 흐름이 아래로 확정됨.
> 상세 변경 내역은 `담당자_피드백_정리_2026-06-15.md` 참조. 본문 1~3장의 개념(매칭 A/B,
> 용어)은 그대로 유효하고, **현재 구체 흐름은 바로 아래 0-A장**을 본다.

## 0-A. 현재 파이프라인 (2026-06-15 기준, 실제 화면 흐름)

```
[① 변경점 작성(master)]                          [② 개발부품마스터 산출]            [출력]
  심의표 PPTX ─┐                                   master(변경점) ─┐
  Base BOM  ─┤ 함께 업로드                          Base BOM(①에서)─┤
             ▼                                                      ▼
   ┌──────────────────┐  검수완료   ┌──────────────────┐   반영   ┌──────────────────┐
   │ 추출 검수        │──────────▶│ 변경점 작성(카드) │────────▶│ apply_master_    │
   │ (원본 표 확인·   │           │ New P/No 부여     │         │  changes         │
   │  수정/추가/삭제) │           │ (TBD/공용/변경)   │         │ +상위전파(TBD)   │
   └──────────────────┘           │ 토글·DnD·Level·  │         └────────┬─────────┘
                                  │ 상위지정·과거참조 │                  │ new_bom(트리)
                                  └──────────────────┘                  ▼
                                                          ┌──────────────────────────┐
                                                          │ 산출물                     │
                                                          │ • 개발부품마스터 xlsx/csv  │
                                                          │   (example.xlsx 템플릿,    │
                                                          │    변경점 상·하위 트리 +   │
                                                          │    공용 Common 포함)       │
                                                          │ • 적용된 BOM xlsx          │
                                                          └──────────────────────────┘
```

핵심 변화(2026-06-15):
1. **입력 동시화**: PPTX와 Base BOM을 ① 단계에서 함께 업로드(이전엔 ②에서 별도). 상태는 탭 간 유지.
2. **추출 검수 단계 신설**: 자동 분류(TBD 빨간 표시) 전에 원본 표를 확인·수정/추가/삭제.
3. **작성 화면 직관화**: 모듈/부모-자식 토글(기본 접힘), 슬라이드 하단 "변경점 요약" 표시,
   드래그앤드롭(아래=하위/위=형제), Level 수정·상위 부품 지정, 수동 부품 추가.
4. **산출물 = 개발부품마스터**: 변경내역을 `example.xlsx` 양식에 채워 xlsx/csv로. **변경점 기준
   상위(조상)·하위(후손) 트리**를 포함하고 재사용 부품은 **Common** 라벨(변경 무관 가지는 제외).
   + 적용된 BOM(전체) xlsx 별도 다운로드.
5. 과거 이력 검색(매칭 B)은 변경점 작성 카드의 **"과거 참조"** 옵션으로만 남음.

## 0. 헷갈리는 진짜 이유 (먼저 읽기)

이 시스템은 **서로 다른 두 가지 "매칭"** 을 한 흐름 안에서 한다. 이 둘을 구분 못 하면
파이프라인이 엉켜 보인다.

| | 매칭 A: "어디를 바꾸나" | 매칭 B: "어떻게 바꾸나" |
| --- | --- | --- |
| 질문 | 이 변경이 **현재 base BOM의 어느 부품**인가? | 비슷한 **과거 변경 사례**는 무엇인가? |
| 대상 | 이번 모델의 **base BOM** | DB에 쌓인 **과거 개발부품 이력** |
| 코드 | `find_target_index` (apply 단계) | `recommend_change_candidates` (검색 단계) |
| 결과 | 바꿀 위치(target row) | 후보(candidate) = 과거 detail row |

지금 시스템은 **B(과거 사례 검색) → 사용자 선택 → A(base BOM에서 위치 찾아 반영)** 순서다.
"후보"라는 단어가 B의 결과인데, 정작 바꾸는 건 A라서 헷갈린다. 이 점을 알고 보면 흐름이 풀린다.

## 1. 한 장 그림

```
[INPUT 3개]                          [시스템]                              [OUTPUT]

① 심의표 PPTX ──추출(LLM)──┐
   (무엇을 바꾸나)          │
                           ▼
                    변경 입력 JSON ──매핑보강──▶ ┌─────────────────┐
   ② (과거 이력 DB) ───────────────────────────▶│ B. 후보 검색     │
      = 과거 개발부품 변경 기록                   │ (dense+BM25)     │
        (dev_part_detail)                        └────────┬────────┘
                                                          │ 후보 목록(top-k)
                                                          ▼
                                                 ┌─────────────────┐
                                                 │ 사용자 선택(HITL)│  ← React 변경 카드
                                                 │ 후보+action 고름 │
                                                 └────────┬────────┘
   ③ base BOM (이번 모델 전체 BOM) ──────────────────────▼
      (무엇을 기준으로 바꾸나)               ┌─────────────────┐
                                            │ A. BOM 반영      │──▶ 최종 BOM
                                            │ (위치찾기+merge) │    (new_bom.xlsx)
                                            │  +상위전파(TBD)  │    +변경리스트
                                            └─────────────────┘
```

핵심: **입력이 3종류**다. ①심의표(변경 내용), ②과거 이력 DB(검색 대상), ③base BOM(반영 기준).
세 개가 어디로 들어가는지만 잡으면 전체가 보인다.

## 2. 핵심 용어 4개

1. **변경 입력 (change input)** — "이 부품을 이렇게 바꾼다"는 한 줄 명세.
   심의표에서 LLM이 뽑거나 사람이 표로 입력. 필드: part_name, change_point, change_reason 등.
2. **과거 이력 (history corpus)** — DB(`dev_part_detail`)에 적재된 **지난 개발 프로젝트들의
   부품 변경 기록**. 현재 12개 프로젝트, 1068행. **검색의 대상**이지 이번 모델의 BOM이 아니다.
3. **base BOM** — 이번에 바꿀 **현재 모델의 전체 부품표**. xlsx 업로드 또는 DB master 선택.
   **반영의 기준**(여기에 변경을 얹어 최종 BOM을 만든다).
4. **후보 (candidate)** — 변경 입력으로 과거 이력을 검색해 나온 **과거 detail row**.
   사용자가 이 중 하나를 골라, 그 부품번호/내용을 base BOM에 반영한다.

## 3. 단계별 상세

### 단계 1. 입력 수집 — 심의표 → 변경 입력 JSON
- 파일: `pptx_text.py`(슬라이드 텍스트) → `change_extraction.py` + `llm.py`(LLM 추출)
- 입력: PPTX 바이트 / 출력: 변경 입력 row 리스트(+중간 CSV 저장)
- LLM은 여기서 **"추출(파싱)"** 에만 쓰인다. 답변 생성(RAG의 G)은 안 한다.
- API: `POST /pptx/extract-changes` · UI: ① 탭

### 단계 2. 매핑 보강 — 부품명 → BOM prefix
- 파일: `module_mapping.py` (사전: `docs/BOM_Code_Mapping_Dictionary.json`)
- "Door Assembly" → prefix `ADC` 식으로 매핑해 검색 후보군을 좁힌다(prefix gate).
- ⚠️ 이 gate가 과하게 좁혀 정답을 빼는 문제가 측정됨 → `검색정확도_골든셋_Level_A_2026-06-14.md`

### 단계 3. (선택) 임베딩 — 변경 입력 텍스트 → 벡터
- 파일: `embeddings.py` (OpenAI, curl 호출). `OPENAI_API_KEY` 없으면 건너뛰고 BM25로만.
- 켜면 dense 검색 가능, 끄면 어휘(BM25)만. UI 사이드바 체크박스.

### 단계 4. 매칭 B — 후보 검색 (이번 시스템의 "retrieval" 핵심)
- 파일: `workflow.py: recommend_change_candidates` (+ `rag/search.py` dense)
- 변경 입력으로 **과거 이력 DB**를 검색해 유사 과거 변경 top-k를 뽑는다.
- 점수 = dense(part_name/변경점/변경사유/combined) + BM25 + identity-text + mapping prefix 가중합.
- 출력: 후보 리스트(각 후보 = 과거 detail row + score + 연관 부품)
- API: `POST /changes/recommend` · UI: ① 탭 결과 / ② 탭 카드

### 단계 5. 사용자 선택 (HITL) — 후보 + action 결정
- 사람이 후보 중 하나를 고르고 action(change / add / delete)을 정한다.
- UI: ② 탭 **변경 카드**(후보 라디오 선택). 이게 React로 새로 만든 핵심 화면.

### 단계 6. 매칭 A + 반영 — base BOM에 merge
- 파일: `workflow.py: apply_selected_changes`
  - `find_target_index`: 선택 후보를 **base BOM의 어느 행**에 적용할지 부품번호/이름으로 찾음(매칭 A)
  - change: 그 행의 new_part_no/qty/사유를 후보 값으로 덮어씀
  - add: 새 행 삽입(+연동 부품 번들), delete: 행+하위 삭제
  - **상위 전파**: 하위가 바뀌면 상위 Assembly 품번을 `TBD`(미정)로 표시(재발번 필요)
- 출력: `new_bom`(최종 BOM), `change_list`(변경 내역), `unmatched`(매칭 실패)
- API: `POST /bom/apply`, `POST /bom/apply/export`(xlsx) · UI: ② 탭 결과

### 단계 7. 출력
- `new_bom.xlsx`(new_bom / change_list / unmatched 시트). UI에서 다운로드.

## 5. 솔직한 평가 — 잘 된 부분 / 재검토할 부분

### 잘 된 부분
- **HITL 2단계(검색 → 사람 선택 → 결정론적 merge)** 구조는 제조 BOM에 적절하다.
  생성형(환각)이 아니라 사람이 고른 걸 규칙대로 합치므로 결과가 검증 가능하다.
- merge 로직 자체는 골든셋에서 변경 실현율 93.6%로 대체로 정상(`tests/golden/compact_oven/`).
- 상위전파 TBD 표시, 하위 subtree 교체 등 실제 회의록 규칙을 반영.

### 헷갈리게 만든 / 재검토할 부분 (정직하게)
1. **검색 대상이 "과거 다른 프로젝트 이력"이라는 점이 직관과 어긋남.** 실무에서 "변경 master를
   쓴다"는 건 보통 **이번 base BOM에서 그 부품을 찾는 일**(매칭 A)에 가깝다. 그런데 시스템의
   메인 검색(B)은 과거 *다른* 모델 이력을 뒤진다. 두 매칭이 한 흐름에 섞여 혼란의 핵심.
   → 측정 결과: "base BOM에서 정답 찾기"는 prefix gate만 꺼도 found@10=100%로 잘 된다.
2. **새 부품번호를 "과거 후보의 new_part_no"로 가져온다.** 진짜 신규개발은 PLM이 새 번호를
   발번하는데, 시스템은 과거 사례 번호를 재사용 제안한다. 맥락에 따라 맞을 수도/아닐 수도.
3. **prefix gate가 정답을 과하게 제외**(측정됨, Level A 보고서). 하드 필터 → soft 가산점 권장.
4. **RAG 생성(G)은 stub로 비어 있고, 안 쓰는 게 맞다**(사용자 확인). 이름이 `sqlite_rag_backend`라
   "RAG 답변"을 기대하면 헷갈리는데, 실제 정체는 **검색 + 결정론적 BOM 편집기**다.

> 결론: "잘못 만든 것"이라기보다 **두 매칭(A/B)이 한 파이프라인에 섞여 있어 개념이 흐려진 것**.
> B(과거사례)는 보조로 두고 A(이번 base BOM 매칭)를 1급으로 명확히 분리하면 훨씬 직관적이 된다.

## 6. 자주 헷갈리는 Q&A

- **Q. /changes/recommend는 base BOM을 검색하나?**
  A. 아니다. **과거 이력 DB**(`dev_part_detail`, 다른 프로젝트들)를 검색한다. base BOM은
  단계 6(apply)에서만 등장한다.
- **Q. 후보(candidate)는 base BOM의 행인가?**
  A. 아니다. **과거 이력의 행**이다. 그걸 골라 base BOM에 "적용"한다.
- **Q. 미정(TBD)은 뭔가?**
  A. 하위 부품이 바뀌어 상위 Assembly도 새 품번이 필요한데 아직 PLM 번호가 없는 상태.
  React에서 보라색 배지로 강조한다.
- **Q. LLM은 어디에 쓰이나?**
  A. **심의표 → 변경 입력 JSON 추출(파싱)** 한 곳뿐. 답변 생성에는 안 쓴다.
- **Q. 임베딩을 꺼도 되나?**
  A. 된다. 끄면 BM25(어휘) 검색만, 켜면 의미(dense) 검색 추가. 정확도·비용 트레이드오프.
