## 0. 한 줄 요약

이 프로젝트는 이름은 `sqlite_rag_backend`지만, **실제로 구현된 것은 RAG의 "R(검색)"
부분**이고 **"G(생성)" 부분은 비어 있다**. 즉 검색·후보추천·BOM반영 파이프라인은
상당히 고도화되어 있으나, 검색된 근거로 **LLM이 답변을 생성하는 진짜 RAG는 아직 stub**
(`rag/pipeline.py:answer_stub`, `GET /rag/ask`)이다. "RAG를 붙인다"는 것은 이
비어 있는 **G를 채우고**, 동시에 **검색 품질(R)을 reranker·RRF·sqlite-vec로 한 단계
올리는 것**으로 정의하는 것이 맞다.

## 1. 현재 진행 상황 (코드 기준 실사)

### 1.1 전체 아키텍처

```text
Streamlit Frontend
  -> FastAPI Backend
    -> SQLite DB 파일 (임베딩을 JSON TEXT 컬럼으로 저장)
      -> OpenAI REST (curl.exe subprocess 호출)
```

- 프론트엔드: Streamlit (`ui/streamlit_app.py`)
- 백엔드: FastAPI (`api/main.py`)
- DB: SQLite 단일 파일 (`data/dev_parts.db`), 벡터 DB 미사용
- LLM/임베딩: OpenAI를 **SDK가 아닌 `curl.exe` subprocess**로 호출
  (`llm.py`, `embeddings.py`) — Windows `OPENSSL_Applink` SSL 오류 회피 목적

### 1.2 구현 완료 — RAG의 "R(검색/추천)"

| 영역 | 파일 | 상태 |
| --- | --- | --- |
| 멀티벡터 Dense 검색 (4필드 cosine) | `rag/search.py` | ✅ 완성, numpy 행렬곱 최적화 + conn 캐싱 |
| BM25 키워드 검색 (SQLite FTS5) | `workflow.py:bm25_scores` | ✅ 완성 |
| Dense + BM25 하이브리드 가중 재정렬 | `workflow.py:hybrid_score` | ✅ 완성 (수동 튜닝 가중치) |
| Prefix 매핑 게이트 (부품군 한정) | `module_mapping.py` + `workflow.py` | ✅ 완성 |
| 변경 의도 동의어 확장 | `workflow.py:CHANGE_SYNONYM_GROUPS` | ✅ 완성 |
| 입력 자동 임베딩 (fallback 포함) | `embeddings.py` | ✅ 완성 |
| 후보별 연관 부품 / subtree 조회 | `workflow.py:get_related_parts` 등 | ✅ 완성 |
| HITL BOM 반영 (change/add/delete/전파) | `workflow.py:apply_selected_changes` | ✅ 완성 |
| XLSX 산출 (외부 라이브러리 없이) | `xlsx.py` | ✅ 완성 |
| PPTX → 변경 JSON 추출 (LLM) | `change_extraction.py`, `pptx_text.py` | ✅ 완성 |

검색 점수식 (현재):

```text
identity_recall =
  0.45*dense_part_name + 0.30*module_part_bm25 + 0.15*identity_text + 0.10*dense_combined

final_score =
  0.45*identity_recall + 0.12*dense_changing_point + 0.10*dense_reason
+ 0.18*change_bm25 + 0.22*change_intent_text + 0.15*mapping_prefix
(+ base_part_no exact match 시 +1.0 가산)
```

### 1.3 미구현 — RAG의 "G(생성)"

```python
# rag/pipeline.py
def answer_stub(conn, question, limit=8):
    matches = search_details(conn, question, limit=limit)
    return {
        "question": question,
        "answer": "LLM answer generation is not wired yet. ...",  # ← 핵심 공백
        "contexts": matches,
    }
```

- `GET /rag/ask`는 **검색 결과만 돌려주고 LLM 답변은 만들지 않는다.**
- 즉 "검색된 근거 → LLM이 한국어로 종합 답변" 단계가 통째로 비어 있다.
- LLM(`llm.py`)은 현재 **추출(extraction)에만** 쓰이고, **생성(generation)에는 미사용.**

### 1.4 현재 기술 스택의 특이점 (중요)

1. **벡터 DB 없음.** 임베딩을 SQLite `TEXT` 컬럼에 JSON 문자열로 저장하고,
   매 질의마다 전체 행을 읽어 Python/numpy로 코사인을 **완전 탐색(brute-force)**.
   (conn당 1회 파싱·정규화 캐싱으로 완화되어 있으나 본질은 O(N) 선형 탐색.)
2. **OpenAI SDK 미사용.** `curl.exe` subprocess로 REST 직접 호출.
   사유: Windows에서 Python `ssl`/OpenAI SDK 경로의 `OPENSSL_Applink` 오류 회피.
3. **LangChain 미사용.** `pyproject.toml` 의존성: fastapi, openai(설치만 됨,
   실호출은 curl), streamlit, uvicorn, requests, certifi, python-dotenv.
4. **RRF·Cross-encoder reranker 없음.** 융합은 손으로 튜닝한 선형 가중합.

## 2. "RAG를 붙인다"의 정의 (이 프로젝트 한정)

RAG = Retrieval + Augmented + Generation. 이 프로젝트는 R은 강하고 G가 없다.
따라서 작업을 두 갈래로 정의한다.

- **(A) G 채우기 — 진짜 RAG 답변 생성** *(가장 큰 공백, 우선순위 1)*
  - 기존 하이브리드 검색으로 근거(BOM/변경이력 row)를 모으고,
  - 그 근거를 LLM에 넣어 **"왜 이 후보인가 / 어떻게 반영해야 하는가"를
    한국어로 근거기반 설명**하게 만든다 (인용·출처 포함, 환각 억제).
  - 적용 위치: `rag/pipeline.py:answer_stub` → 실제 `answer()` 로 교체,
    `GET /rag/ask` 응답에 `answer` + `citations` 채움.

- **(B) R 강화 — 검색 품질·확장성 업그레이드** *(우선순위 2)*
  - sqlite-vec 도입으로 brute-force 코사인 → ANN 인덱스 검색.
  - RRF 융합 + Cross-encoder reranker로 정밀도 향상.
  - 질의 재작성(Query Rewriting)/HyDE로 입력 표현 흔들림 흡수.

## 3. 웹 검색으로 조사한 2026년 RAG 개선 기법

> "RAG는 죽지 않았다 — 2026년에도 실제로 통하는 패턴"은 결국
> **하이브리드 검색 + RRF + Cross-encoder 재정렬 + (선택) 질의 재작성·컨텍스트 보강**
> 조합으로 수렴한다. 아래는 본 프로젝트에 **바로 가져올 가치가 있는 것**만 선별.

### 3.1 sqlite-vec (가장 임팩트 큰 도입 후보)

- SQLite **확장(extension)** 으로, `vec0` 가상 테이블에 임베딩을 넣고
  ANN/정확 KNN 검색을 SQL로 수행. **현재의 "JSON 파싱 + 전 행 코사인"을 대체.**
- 같은 SQLite 안에서 **FTS5(BM25)와 나란히 두고 하이브리드 검색** 구성 가능 →
  지금의 단일 `.db` 파일 배포 철학(Docker·PG 없이)과 완벽히 일치.
- **LangChain에 `SQLiteVec` VectorStore 통합이 이미 존재** (`langchain_community`).
- 비용: `sqlite-vec` 파이썬 패키지 추가, 스키마에 `vec0` 테이블 추가, 적재 경로 수정.

### 3.2 RRF (Reciprocal Rank Fusion)

- 현재는 손으로 튜닝한 선형 가중합(가중치 8개)을 매번 데이터에 맞춰 조정.
- RRF는 **점수 스케일이 다른 두 랭킹(Dense·BM25)을 순위만으로 안정 융합** →
  가중치 튜닝 부담을 크게 줄이고 도메인 변동에 강함.
- 비용: `workflow.py`에 `1/(k+rank)` 합산 함수 추가 (수십 줄), 기존 가중합과 A/B 비교.

### 3.3 Cross-encoder Reranker (정밀도 1순위 개선)

- 1차로 하이브리드가 상위 후보 N개를 빠르게 추리고(bi-encoder),
  2차로 **Cross-encoder가 (질의, 후보)를 함께 보고 정밀 재정렬**.
- 보고된 효과가 가장 큰 단일 기법. BOM처럼 "정체성은 비슷한데 변경의도가 다른"
  후보를 가르는 데 특히 유효.
- 선택지: 로컬 BGE-reranker(오프라인·무료, 다국어) 또는 Cohere Rerank(API).
  사내망/오프라인 제약이면 **로컬 BGE-reranker 권장**.

### 3.4 Query Rewriting / HyDE (선택)

- 사용자의 거친 한 줄 변경 입력을 LLM이 **검색 친화적 질의로 재작성**하거나,
  **가상의 이상적 답변(HyDE)을 만들어 그것으로 검색** → 표현 불일치 흡수.
- 본 프로젝트는 이미 동의어 확장으로 부분 대응 중이므로, **G 도입 후 추가**가 합리적.

### 3.5 Contextual Retrieval (선택, 적재 단계)

- 각 BOM row(청크)에 **상위 어셈블리/모델 맥락 문장 1~2줄을 LLM으로 덧붙여 임베딩**.
- BOM은 계층 구조라 행 단독으로는 맥락이 빈약 → 검색 recall 개선 여지.
- 비용: 적재 시 LLM 호출 1회/행 (1회성). 데이터가 1천 행대라 충분히 감당 가능.

## 4. LangChain 적용 가능성 (사용자 요청: "langchain으로 쓸 수 있으면 좋고")

### 4.1 결론

**부분 도입을 권장.** LangChain은 이 프로젝트에서 **R 전체를 갈아엎는 도구가 아니라,
G(생성 체인)와 reranker 오케스트레이션을 빠르게 붙이는 접착제**로 쓰는 게 맞다.

### 4.2 LangChain이 잘 맞는 부분

| LangChain 구성요소 | 이 프로젝트에서의 역할 |
| --- | --- |
| `SQLiteVec` VectorStore | sqlite-vec를 LangChain 표준 Retriever로 노출 |
| `BM25Retriever` + `EnsembleRetriever` | 기존 Dense+BM25 하이브리드를 표준화 (RRF 내장) |
| `CrossEncoderReranker` (ContextualCompression) | 3.3의 reranker를 체인에 끼움 |
| `create_retrieval_chain` / LCEL | 3.x의 **G(근거기반 답변 생성)** 를 표준 패턴으로 구현 |

### 4.3 반드시 짚어야 할 제약 (현실 경고)

- 현재 코드가 **OpenAI SDK 대신 curl을 쓰는 이유**(Windows `OPENSSL_Applink`)는
  LangChain의 `langchain-openai`(httpx 기반)에서도 **재현될 수 있다.**
  → 도입 전에 **사내망/현 PC에서 `langchain-openai` 임베딩 1회 호출이 SSL 통과하는지
  먼저 검증**해야 한다. 통과 못 하면:
  - (a) 임베딩/LLM은 기존 curl 경로 유지 + LangChain은 **Retriever/Reranker/프롬프트
    조립만** 담당하는 하이브리드 구성, 또는
  - (b) 로컬 임베딩/리랭커(sentence-transformers, BGE)로 전환해 외부 SSL 의존 제거.
- LangChain은 의존성이 무겁다(전이 의존 다수). "Docker·PG 없이 가벼운 단일 파일"
  철학과 상충하므로 **`langchain-core` + 필요한 community 모듈만 최소 설치** 권장.

## 5. 한계점 정리

### 5.1 구조적 한계

1. **검색 확장성**: 임베딩을 JSON TEXT로 저장 + 전 행 코사인은 O(N).
   현재 ~1천 행대라 문제없지만, 수만 행 이상에서 선형 악화. → sqlite-vec로 해소.
2. **생성 부재**: 진짜 RAG 답변(G)이 없어 "검색기 + 추천기"에 가깝다.
3. **융합 방식**: 손튜닝 선형 가중치 8개는 데이터가 바뀔 때마다 재튜닝 필요. → RRF.
4. **Reranker 없음**: 정체성 유사·의도 상이 후보 분별력이 가중합 한계에 묶임.
5. **외부 의존 취약성**: OpenAI 미가용/SSL 실패 시 BM25 fallback으로 품질 저하.
   (graceful degradation은 되어 있으나 답변 품질은 떨어짐.)

### 5.2 데이터/도메인 한계

6. **한국어 토크나이징**: 정규식 토큰 기반(형태소 분석 없음). 복합명사·조사 처리 한계.
7. **컨텍스트 빈약**: 과거 데이터의 변경사유(약 47%)/변경점(약 24%)이 희소
   (코드 주석에 명시). 근거가 비어 있으면 G의 답변 품질도 제한됨.
8. **평가셋 부재 → 일부 해소(2026-06-14)**: end-to-end 회귀 골든셋을
   `tests/golden/compact_oven/`에 구축함 (Compact Oven 실제 1건: base BOM + 변경이력
   master → 최종 BOM 정답). `apply_selected_changes`의 변경 실현율을 회귀 추적.
   현재 baseline: 변경 실현율 0.936, 삭제 1.0. **단 N=1이고 검색(retrieval) 정확도는
   아직 미평가** → 케이스 추가·Level A(검색) 라벨링이 다음 과제.

## 6. 향후 진행 방향 (우선순위順 로드맵)

### Phase 0 — 평가셋 먼저 (0.5일)
- 실제 변경 입력 10~20건에 대해 "정답 detail_id"를 라벨링한 골든셋 CSV 작성.
- `recommend_change_candidates`의 Top-1/Top-5 hit율을 찍는 작은 스크립트.
- 이후 모든 개선을 이 숫자로 검증. **이게 없으면 나머지는 감으로 하는 것.**

### Phase 1 — G 채우기 (진짜 RAG 답변) (1~2일) ★최우선
- `rag/pipeline.py`에 `answer()` 구현:
  하이브리드 검색 → 상위 K 근거를 프롬프트로 조립 → `llm.chat_json`으로
  **근거기반 한국어 답변 + 인용(detail_id) + "근거 없음" 회피문**.
- `GET /rag/ask` 응답에 `answer`, `citations`, `contexts` 동시 반환.
- Streamlit에 "질문하기" 탭 추가 (선택).
- 환각 억제 규칙: "제공된 컨텍스트에 없으면 모른다고 답한다"를 시스템 프롬프트에 명시.

### Phase 2 — Reranker + RRF (1일)
- RRF 융합 함수 추가, 기존 가중합과 Phase 0 평가셋으로 A/B.
- 로컬 BGE Cross-encoder reranker를 상위 N 후보에 적용 (오프라인·무료).

### Phase 3 — sqlite-vec 마이그레이션 (1~2일)
- 스키마에 `vec0` 가상 테이블 추가, 적재 경로(`loader.py`, `embedding_csv.py`) 수정.
- `rag/search.py`의 brute-force 코사인을 sqlite-vec KNN으로 교체 (인터페이스 유지).
- FTS5와 결합한 SQL 레벨 하이브리드 검색.

### Phase 4 — LangChain 표준화 (선택, 0.5~1일)
- **먼저 `langchain-openai` SSL 통과 검증.** 통과 시 `SQLiteVec` +
  `EnsembleRetriever` + `CrossEncoderReranker` + `create_retrieval_chain`으로
  Phase 1~3을 표준 컴포넌트로 재구성. 실패 시 4.3-(a)/(b) 하이브리드 유지.

### Phase 5 — Query Rewriting / Contextual Retrieval (선택)
- G가 안정된 뒤, 입력 재작성·청크 컨텍스트 보강으로 recall 추가 개선.

## 8. 즉시 시작 가능한 첫 걸음 (제안)

가장 ROI가 높은 것은 **Phase 1(G 채우기)** 이다. 기존 `llm.py`(curl 기반)를 그대로
재사용하므로 **새 의존성 0, SSL 위험 0**으로 진짜 RAG 답변을 붙일 수 있고,
사용자가 체감하는 "RAG가 붙었다"는 변화가 가장 크다.

원하시면 이어서:
1. Phase 0 평가셋 스크립트 + Phase 1 `answer()` 구현 (의존성 추가 없음), 또는
2. Phase 4 검증용 — 현 PC에서 `langchain-openai` 임베딩 SSL 통과 여부 1회 테스트

중 무엇부터 진행할지 알려주시면 바로 코드로 들어가겠습니다.
